# 6장 프록시

- 웹 프록시 서버는 중개자다.
- 프록시는 클라이언트와 서버 사이에 위치하여 그들 사이의 HTTP 메시지를 정리하는 중개인처럼 동작한다.

- HTTP 프록시와 웹 게이트웨이를 비교하고 HTTP 프록시 어떻게 배치되는지
- 프록시가 실제 네트워크에서 어떻게 배치되어 있는지 그리고 트래픽이 어떻게 프록시 서버로 가게 되는지
- 브라우저에서 프록시를 사용하려면 어떻게 설정해야 하는지
- HTTP 프록시 요청이 서버 요청과 어떻게 다른지, 프록시가 어떻게 브라우저의 동작을 미묘하게 바꾸는지
- 일련의 프록시 서버들을 통과하는 메시지의 경로를 Via 헤더와 TRACE 메서드를 이용해 기록하는 방법
- 프록시에 기반한 HTTP 접근 제어
- 어떻게 프록시가 클라이언트와 서버 사이에서 각각의 다른 기능과 버전들을 지원하면서 상호작용 할 수 있는지

## 6.1 웹 중개자

- 웹 프록시 서버는 클라이언트의 입장에서 트랜잭션을 수행하는 중개인이다.
- HTTP 프록시 서버는 웹 서버이기도 하고 웹 클라이언트이기도 하다.
- 프록시는 HTTP 클라이언트의 요청을 받게 되므로, 반드시 웹 서버처럼 요청과 커네션을 적절히 다루고 응답을 돌려줘야 한다.
- 동시에 프록시는 요청을 서버로 보내기도 하므로 요청을 보내고 응답을 받는 올바를 HTTP 클라이언트처럼 동작해야 한다.

- 중앙 집중형 프록시를 관리하는 게 더 비용효율이 높고 쉽다.

#### 개인 프록시

### 6.1.2 프록시 대 게이트웨이

- 프록시는 같은 프로토콜을 사용하는 둘 이상의 애플리케이션을 연결하고 게이트웨이는 서로 다른 프로토콜을 사용하는 둘 이상을 연결한다.
- 게이트웨이는 클라이언트와 서버가 서로 다른 프로토콜로 말하더라도 서로 간의 트랜잭션을 완료할 수 있도록 해주는 프로토콜 변환기처럼 동작한다.
- 실질적으로 프록시와 게이트웨이의 차이점은 모호하다.

## 6.3 프록시는 어디에 있는가?

- 어떻게 프록시가 네트워크에 배치되는가
- 어떻게 프록시의 연쇄가 계층을 이루는가
- 어떻게 트래픽이 올바르게 프록시를 찾아가는가

### 6.3.1 프록시 서버 배치

#### 출구 프록시

- 로컬 네트워크의 출구에 배치되어 로컬 네트워크와 인터넷 사이를 오가는 트래픽을 제어한다.
- 회사에서 인터넷으로 나가는 요청을 필터링하거나 성능 개선을 위해 사용된다.

#### 접근(입구) 프록시

- ISP 접근 지점에 위치하여 고객들로부터의 모든 요청을 종합적으로 처리한다.
- 다운로드 속도 개선을 위한 캐시 프록시로 사용되며, 사용자들의 트래픽을 처리한다.

#### 대리 프록시

- 웹 서버 바로 앞에 위치하여 웹 서버로 향하는 모든 요청을 처리한다.
- 보안 기능을 추가하거나 빠른 웹 서버 캐시를 느린 웹 서버 앞에 놓아 성능을 개선한다.

#### 네트워크 교환 프록시

- 네트워크 사이의 인터넷 피어링 교환 지점에 놓여 캐시를 통해 인터넷 혼잡을 완화하고 트래픽 흐름을 감시한다.

### 6.3.2 프록시 계층

- 프록시들은 프록시 계층이라고 불리는 연쇄를 구성할 수 있다.
- 프록시 계층에서 프록시 서버들은 부모와 자식의 관계를 갖는다.

#### 프록시 계층 콘텐츠 라우팅

- 프록시 서버는 여러 가지 판단 근거에 의해 메시지를 다양하고 유동적인 프록시 서버와 원 서버들의 집합에게 보낼 수 있다.

- 동적 부모 선택의 몇 가지 예
  - 부하 균형
  - 지리적 인접성에 근거한 라우팅
  - 프로토콜 / 타입 라우팅
  - 유료 서비스 가입자들을 위한 라우팅

## 6.5 프록시 요청의 미묘한 특징들

- 프록시 요청의 URI는 서버 요청과 어떻게 다른가
- 인터셉트 프록시와 리버스 프록시는 어떻게 서버 호스트 정보를 알아내기 어렵게 만드는가
- URI 수정에 대한 규칙
- 프록시는 브라우저의 똑똑한 URI 자동완성이나 호스트 명 확장 기능에 어떻게 영향을 주는가

### 6.5.1 프록시 URI는 서버 URI와 다르다.

- 클라이언트가 프록시 대신 서버로 요청을 보내면 요청의 URI가 달라진다.
- 클라이언트가 프록시를 사용하지 않도록 설정되어 있다면, 부분 URI를 보낸다.
  - 예: `GET /index.html HTTP/1.0`
- 클라이언트가 프록시를 사용하도록 설정되어 있다면 완전한 URI를 보낸다.
  - 예: `GET http://www.example.com/index.html HTTP/1.0`
- 프록시는 목적지 서버와 커넥션을 맺기 위해 스킴, 호스트, 포트번호가 포함된 완전한 URI가 필요하다.

### 6.5.2 가상 호스팅에서 일어나는 같은 문제

- 명시적인 프록시는 요청 메시지가 완전한 URI를 갖도록 함으로써 이 문제를 해결함
- 가상으로 호스팅되는 웹 서버는 호스트와 포트에 대한 정보가 담겨 있는 Host 헤더를 요구한다.

### 6.5.3 인터셉트 프록시는 부분 URI를 받는다.

- 클라이언트는 자신이 프록시와 대화하고 있음을 알지 못하므로 완전한 URI를 보내지 않고 부분 URI를 보낸다.
- 인터셉트 프록시는 원 서버의 IP 주소와 포트번호를 알아내기 위해 다른 기법들을 사용해야 한다.
- 대리 프록시의 경우 원 서버의 주소와 포트번호가 프록시에 설정되어 있으므로 문제가 없다.

### 6.5.4 프록시는 프록시 요청과 서버 요청을 모두 다룰 수 있다.

- 프록시는 명시적인 프록시 요청에 대해서는 완전한 URI를 사용하고 아니면 부분 URI를 사용해야 하며, 웹 서버 요청의 경우에는 가상 Host 헤더를 사용해야 한다.

### 6.5.5 전송 중 URI 변경

- 일반적으로 프록시 서버는 가능한 한 관대하도록 애써야 한다.
- 프록시는 메시지를 다음 홉으로 보내기 전에 URI를 표준 형식으로 정규화해야 한다.
- 상호운용성 문제를 피하기 위해 HTTP 명세에서 허용하는 범위 내에서 URI를 변경할 수 있다.

### 6.5.6 URI 클라이언트 자동확장과 호스트 명 분석

- 브라우저는 사용자가 타이핑한 URI를 가지고 자동으로 호스트 명을 확장한다.
- 예를 들어 "yahoo"를 입력하면 브라우저가 자동으로 "www.yahoo.com"으로 확장한다.
- 프록시의 존재 여부에 따라 이러한 확장 기능의 동작이 달라질 수 있다.

### 6.5.7 프록시 없는 URI 분석(URI Resolution)

- 프록시가 없을 때, 사용자가 URI를 입력하면 브라우저는 그것을 이용해 서버에 접속을 시도한다.
- URI가 유효하지 않으면 브라우저는 몇 가지 자동확장 기법을 시도한다.
- 호스트 명에 자동으로 "www" 접두사와 ".com" 접미사를 붙이는 등의 방법을 사용한다.

### 6.5.8 명시적인 프록시를 사용할 때의 URI 분석

- 브라우저는 명시적인 프록시가 있는 경우 부분 호스트 명을 자동확장하지 않는다.
- URI를 프록시에 넘기기 전에 자동확장하지 않는 이유는, 프록시가 자체적인 DNS를 가지고 있을 수 있고, 사용자가 의도한 것과 다른 사이트로 연결될 수 있기 때문이다.

### 6.5.9 인터셉트 프록시를 이용한 URI 분석

- 인터셉트 프록시를 사용할 때는 클라이언트가 프록시를 인지하지 못하므로 평상시와 같이 URI 자동확장이 동작한다.
- 이는 프록시가 없을 때와 동일한 방식으로 동작하므로 사용자 경험에 영향을 주지 않는다.

## 6.6 메시지 추적

### 6.6.1 Via 헤더

- Via 헤더 필드는 메시지가 지나는 각 중간 노드(프록시나 게이트웨이)의 정보를 나열한다.
- 메시지가 또 다른 노드를 지날 때마다, 중간 노드는 Via 목록의 끝에 반드시 추가되어야 한다.
- Via 헤더 필드는 메시지의 전달을 추적하고 메시지 루프를 진단하고 요청을 보내고 그에 대한 응답을 돌려주는 과정에 관여하는 모든 메시지 발송자들의 프로토콜을 다루는 능력을 알아보기 위해 사용된다.
- 프록시는 또한 네트워크의 라우팅 루프를 탐지하기 위해 Via 헤더를 사용할 수 있다.

#### Via 문법

- Via 헤더 필드는 쉼표로 구분된 경유지의 목록이다.
- Via waypoint는 프로토콜 이름(선택, 기본은 HTTP), 프로토콜 버전(필수), 노드 이름(필수), 코멘트(선택)의 최대 4개의 구성요소를 담을 수 있다.

- 프로토콜 버전
- 노드 이름
- 노드 코멘트
- Via 요청과 응답 경로
  - 요청 메시지와 응답 메시지 모두 프록시를 지나므로 둘 중 모두 Via 헤더를 가진다.
  - 응답의 Via 헤더는 거의 언제나 요청의 Via 헤더와 반대다.

#### Via와 게이트웨이
- 몇몇 프록시는 서버에게 비 HTTP 프로토콜을 사용할 수 있는 게이트웨이 기능을 제공한다.

#### Server 헤더와 Via 헤더

#### Via가 개인정보 보호와 보안에 미치는 영향

- Via 헤더는 프록시 서버의 호스트 명과 버전을 노출시키므로 보안에 취약할 수 있다.
- 악의적인 사용자가 Via 헤더 정보를 통해 네트워크 구조나 사용 중인 프록시 소프트웨어의 취약점을 파악할 수 있다.
- 조직 내부의 네트워크 구조가 외부에 노출되는 것을 막기 위해, 방화벽 프록시는 내부 프록시의 정보를 Via 헤더에서 제거하거나 익명화할 수 있다.
- 개인정보 보호를 위해 프록시 호스트 명을 가명으로 대체하는 것도 가능하다.

### 6.6.2 Trace 메서드

- 프록시 서버는 메시지가 전달될 때 메시지를 바꿀 수 있다.
- 헤더가 추가되거나, 변경되거나, 삭제될 수 있으며, 본문이 다른 형식으로 변환될 수 있다.
- HTTP/1.1의 TRACE 메서드는 요청 메시지를 프록시의 연쇄를 따라가면서 어떤 프록시를 지나가고 어떻게 각 프록시가 요청 메시지를 수정하는지 관찰 / 추적할 수 있도록 해준다.

#### MAX-Forwards

- TRACE와 OPTIONS 요청의 무한 루프를 방지하기 위해 Max-Forwards 헤더를 사용한다.
- Max-Forwards 헤더는 이 요청이 몇 번이나 더 다음 홉으로 전달될 수 있는지를 나타내는 정수 값을 담고 있다.
- Max-Forwards 값이 0이면 프록시는 요청을 전달하지 않고 클라이언트에게 응답을 돌려준다.
- 각 프록시를 지날 때마다 Max-Forwards 값이 1씩 감소하며, 0에 도달하면 더 이상 전달되지 않는다.
- 이를 통해 프록시 체인의 특정 지점을 테스트하거나 무한 루프를 방지할 수 있다.

## 6.7 프록시 인증

- 프록시는 접근 제어 장치로서 제공될 수 있다.
- HTTP는 사용자가 유효한 접근 권한 자격을 프록시에 제출하지 않는 한 콘텐츠에 대한 요청을 차단하는 프록시 인증이라는 메커니즘을 정의하고 있다.

## 6.8 프록시 상호 운용성

- 프록시 서버는 서로 다른 프로토콜을 구현했을 수도 있고 골치 아프게 이상한 동작을 할 수도 있는 클라이언트와 서버 사이를 중개해야 한다.

### 6.8.1 지원하지 않는 헤더와 메서드 다루기

- 프록시는 이해할 수 없는 헤더 필드는 반드시 그대로 전달해야 하며, 같은 이름의 헤더 필드가 여러 개 있는 경우에는 그들의 상대적인 순서도 반드시 유지해야 한다.

### 6.8.2 OPTIONS: 어떤 기능을 지원하는지 알아보기

- 클라이언트는 OPTIONS를 이용해 서버의 능력을 먼저 알아낼 수 있다.

### 6.8.3 Allow 헤더

- Allow 엔티티 헤더 필드는 요청 URI에 의해 식별되는 자원에 대해 지원되는 메서드들이나 서버가 지원하는 모든 메서드(요청 URI가 \*인 경우)를 열거한다.
- Allow 헤더는 새 리소스가 지원했으면 하는 메서드를 추천하기 위해 요청 헤더로 사용될 수 있다.
- 만약 프록시가 지정된 모든 메서드를 이해할 수는 없다고 해도, 프록시는 Allow 헤더 필드를 수정할 수 없다. 
- 왜냐하면 클라이언트는 원 서버와 대화하는 다른 경로를 갖고 잇을 수도 있기 때문이다.
