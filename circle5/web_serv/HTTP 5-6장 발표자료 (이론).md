# Part 0: nginx란 무엇인가?

## nginx 소개

### nginx의 탄생

**2004년, Igor Sysoev가 개발**

- 러시아의 개발자
- 당시 문제: **C10K 문제** (동시 연결 10,000개 처리의 어려움)
- Apache는 멀티프로세스 방식으로 메모리 과다 사용
- 해결책: 이벤트 기반 아키텍처

**이름의 유래:**

- engine x → nginx
- 발음: "엔진엑스"

### nginx가 하는 일

nginx는 **3가지 역할**을 할 수 있습니다:

**1. 웹 서버 (Web Server)**

- 클라이언트 ←→ nginx ←→ 정적 파일 (HTML, CSS, 이미지)
- 정적 파일을 빠르게 제공

**2. 리버스 프록시 (Reverse Proxy)**

- 클라이언트 ←→ nginx ←→ 백엔드 서버들
- 실제 서버를 숨기고 중개

**3. 로드 밸런서 (Load Balancer)**

- 클라이언트의 요청을 여러 서버에 분산
- 서버1, 서버2, 서버3에 부하 분산

---

### nginx vs Apache

**시장 점유율 (2026년 기준):**

- nginx: 약 34%
- Apache: 약 31%
- Cloudflare, LiteSpeed 등: 나머지

| 특징                  | Apache              | nginx                  |
| --------------------- | ------------------- | ---------------------- |
| **아키텍처**    | 멀티프로세스/스레드 | 이벤트 기반            |
| **메모리**      | 많이 사용           | 적게 사용              |
| **동시 연결**   | 수백~수천           | 수만~수십만            |
| **정적 파일**   | 느림                | 빠름                   |
| **동적 콘텐츠** | 내장 (mod_php 등)   | 외부 연동 (PHP-FPM 등) |
| **설정**        | .htaccess 분산 가능 | 중앙 집중식            |
| **확장성**      | 모듈 많음           | 모듈 적지만 효율적     |

**언제 어떤 걸 쓸까?**

- **Apache**: 공유 호스팅, .htaccess 필요, 다양한 모듈 필요
- **nginx**: 대용량 트래픽, 정적 파일 많음, 리버스 프록시

---

### nginx의 핵심: 이벤트 기반 아키텍처

#### 전통적인 방식 (Apache prefork):

**연결마다 프로세스 생성:**

- 연결1 → 프로세스1 (메모리 10MB)
- 연결2 → 프로세스2 (메모리 10MB)
- 연결3 → 프로세스3 (메모리 10MB)
- ...
- 연결100 → 프로세스100 (메모리 1GB!)

**결과:** 연결이 많아지면 메모리 부족

#### nginx 방식 (이벤트 기반):

**워커 프로세스가 여러 연결 동시 관리:**

- 마스터 프로세스
  - 워커 프로세스 1 (CPU 코어 1개)
    - 연결1 (대기 중)
    - 연결2 (데이터 처리 중) ← 지금 처리
    - 연결3 (대기 중)
    - ... (수천 개)
  - 워커 프로세스 2 (CPU 코어 1개)
    - ...

**결과:** 워커 하나가 수천 개 연결 동시 관리 (메모리 효율적)

#### 비유로 이해하기:

- **Apache**: 손님 1명당 직원 1명 배정 (비효율)

  - 손님이 주문 기다리는 동안 직원은 그냥 서 있음
- **nginx**: 직원 1명이 여러 손님 동시에 서빙 (효율)

  - 한 손님이 메뉴 고르는 동안 다른 손님 주문 받음

---

### nginx가 빠른 이유

**1. 비동기 I/O (epoll/kqueue)**

- 파일 읽기 요청 → OS에 맡김 → 다른 일 처리 → 준비되면 처리
- 기다리지 않고 계속 다른 일 처리

**2. 적은 메모리 사용**

- 워커 프로세스: 보통 2~4개 (CPU 코어 수만큼)
- 연결당 메모리: 약 1~2KB

**3. CPU 캐시 효율**

- 프로세스가 적어서 컨텍스트 스위칭 적음
- CPU가 효율적으로 동작

---

### nginx 실사용 예시

**전세계 유명 사이트들이 사용:**

- **Netflix** (동영상 스트리밍)
- **Airbnb** (웹 서비스)
- **WordPress.com** (블로그)
- **GitHub** (코드 호스팅)
- **CloudFlare** (CDN)

**왜 이 회사들이 nginx를 쓸까?**

- 높은 동시 접속 처리
- 적은 리소스로 많은 트래픽 처리
- 안정성

---

### 왜 우리가 nginx를 배우는가?

**1. HTTP 이론의 실제 구현**

- 웹서버 7단계가 실제로 어떻게 작동하는지
- 프록시가 실제로 어떻게 동작하는지

**2. webserv 과제와의 연관성**

- nginx는 C++로 작성됨
- 웹서버 구조를 이해하는 데 도움
- 설정 파일 파싱, 이벤트 처리 등 참고 가능

**3. 실무 활용**

- 가장 널리 쓰이는 웹서버 중 하나
- 인프라 엔지니어의 필수 지식

---

### nginx의 한계

**단점도 있습니다:**

1. 동적 모듈 로딩 제한 (컴파일 시 포함 필요)
2. .htaccess 같은 분산 설정 불가
3. 복잡한 rewrite 규칙 작성 어려움
4. 디버깅이 Apache보다 어려움

**하지만:**

- 장점이 단점을 훨씬 상회
- 대부분의 현대적인 웹 서비스에 적합

---

### 정리

**nginx는:**

- ✓ 이벤트 기반 웹서버
- ✓ 높은 성능과 낮은 메모리
- ✓ 웹서버 + 리버스 프록시 + 로드밸런서
- ✓ HTTP 이론을 실제로 확인할 수 있는 도구

**이제 nginx의 관점에서 HTTP 5-6장 내용을 살펴봅시다!**

# Part 1: 웹서버 (5장)

## 1. 웹서버의 역할

### 웹서버란?

- HTTP 요청을 처리하고 응답을 제공하는 소프트웨어/하드웨어
- HTTP 및 TCP 처리 구현
- 리소스 관리 및 설정 제공

### 웹서버의 형태

**1. 다목적 소프트웨어 웹서버**

- Apache, nginx, IIS 등
- 범용 컴퓨터에서 동작

**2. 임베디드 웹서버**

- IoT 기기, 프린터 등에 내장
- 제한된 리소스 환경

---

## 2. 웹서버가 하는 7단계

웹서버는 다음 7단계로 HTTP 요청을 처리합니다:

**1. 커넥션을 맺는다**

- 클라이언트의 접속을 받아들이거나, 원치 않는 클라이언트라면 닫는다

**2. 요청을 받는다**

- HTTP 요청 메시지를 네트워크로부터 읽어들인다

**3. 요청을 처리한다**

- 요청 메시지를 해석하고 행동을 취한다

**4. 리소스에 접근한다**

- 메시지에서 지정한 리소스에 접근한다

**5. 응답을 만든다**

- 올바른 헤더를 포함한 HTTP 응답 메시지를 생성한다

**6. 응답을 보낸다**

- 응답을 클라이언트에게 돌려준다

**7. 트랜잭션을 로그로 남긴다**

- 로그파일에 트랜잭션 완료에 대한 기록을 남긴다

### nginx에서는 어떻게 동작하나?

**1. 커넥션 설정**

- listen 디렉티브로 포트 설정 (예: listen 80)

**2. 요청 수신 설정**

- client_header_timeout: 헤더 읽기 시간 제한
- client_body_timeout: 본문 읽기 시간 제한

**4. 리소스 접근**

- root: 파일 시스템의 루트 디렉터리 지정

**7. 로깅**

- access_log: 접근 로그
- error_log: 에러 로그

---

## 3. 커넥션 처리 아키텍처

웹서버가 동시에 여러 클라이언트를 처리하는 방법은 크게 3가지입니다.

### 3.1 단일 스레드 웹서버

**동작 방식:**

- 요청1 → [처리] → 응답1 → 요청2 → [처리] → 응답2

**특징:**

- 한 번에 하나씩 순차 처리
- 심각한 성능 문제 발생
- 한 요청이 처리되는 동안 다른 모든 요청 대기

**사용 사례:**

- 간단한 테스트 서버
- 실제 프로덕션에서는 거의 사용 안 함

---

### 3.2 멀티프로세스/멀티스레드 웹서버

**동작 방식:**

- 요청1 → [프로세스1] → 응답1
- 요청2 → [프로세스2] → 응답2
- 요청3 → [프로세스3] → 응답3

**특징:**

- 여러 요청 동시 처리
- Apache의 기본 방식 (prefork, worker)
- 프로세스/스레드마다 메모리 사용
- 최대 프로세스 수 제한 필요

**Apache prefork 모델:**

- 시작 서버 수: 5개
- 최소 유휴 서버: 5개
- 최대 유휴 서버: 10개
- 최대 워커: 150개

**장점:**

- 구현이 비교적 간단
- 안정적 (프로세스 하나 죽어도 다른 거 영향 없음)

**단점:**

- 메모리 많이 사용
- 컨텍스트 스위칭 오버헤드
- C10K 문제 대응 어려움

---

### 3.3 다중 I/O 서버 (이벤트 기반)

**동작 방식:**

- [이벤트 루프]
  - 요청1 (일부 처리)
  - 요청2 (일부 처리)
  - 요청3 (일부 처리)
  - 요청1 (계속 처리)

**특징:**

- 모든 커넥션을 동시에 감시
- 유휴 커넥션에 리소스 낭비 없음
- **nginx의 방식**

**nginx 설정:**

- worker_connections: 워커 하나당 최대 커넥션 (예: 1024)
- use epoll: Linux에서 epoll 사용
- worker_processes auto: CPU 코어 수만큼 워커 생성

**장점:**

- 메모리 효율적
- C10K 문제 해결
- 높은 동시성

**단점:**

- 구현 복잡도 높음
- 디버깅 어려움

---

### 아키텍처 비교표

| 특성           | 단일 스레드 | 멀티프로세스 | 이벤트 기반    |
| -------------- | ----------- | ------------ | -------------- |
| 동시 처리      | ✗          | ✓           | ✓             |
| 메모리 효율    | ✓          | ✗           | ✓             |
| C10K 문제 대응 | ✗          | △           | ✓             |
| 복잡도         | 낮음        | 중간         | 높음           |
| 예시           | 간단한 서버 | Apache       | nginx, Node.js |

**C10K 문제란?**

- Concurrent 10,000 connections
- 동시에 10,000개 이상의 클라이언트 연결을 처리하는 문제
- 멀티프로세스 방식으로는 메모리 부족으로 해결 어려움
- 이벤트 기반 아키텍처로 해결

## 4. 리소스 매핑과 접근

웹서버는 URI를 실제 리소스로 매핑해야 합니다.

### 4.1 Document Root (docroot)

**개념:**

- 웹 콘텐츠를 위한 특별한 폴더
- 요청 URI를 파일 시스템 경로로 변환

**변환 예시:**

- 요청: GET /images/logo.png
- docroot: /var/www/html
- 실제 파일: /var/www/html/images/logo.png

**보안 주의사항:**

- 상대 경로 공격 방지 필요
- GET /../../../etc/passwd 같은 요청 차단
- 웹서버는 자동으로 .. 경로를 제거하거나 정규화

---

### 4.2 가상 호스팅 (Virtual Hosting)

**개념:**

- 하나의 웹서버에서 여러 웹사이트 호스팅
- Host 헤더 또는 IP 주소로 구분

**동작 방식:**

**사이트 1: www.example.com**

- 루트: /var/www/example.com
- 로그: /var/log/nginx/example.com.log

**사이트 2: www.another.com**

- 루트: /var/www/another.com
- 로그: /var/log/nginx/another.com.log

**요청 구분:**

- GET / HTTP/1.1
- Host: www.example.com
- → /var/www/example.com/index.html 반환
- GET / HTTP/1.1
- Host: www.another.com
- → /var/www/another.com/index.html 반환

**Host 헤더가 없거나 매칭 안 되면:**

- 기본 서버 (default_server) 사용
- 또는 연결 종료

---

### 4.3 디렉터리 목록

**디렉터리 요청 시 서버의 선택지:**

**1. 에러 반환**

- 403 Forbidden 반환

**2. 기본 색인 파일 반환 (가장 일반적)**

- index.html, index.htm, index.php 등 찾기
- 있으면 해당 파일 반환

**3. 디렉터리 목록 HTML 생성**

- 자동으로 파일 목록 생성
- 파일명, 크기, 수정일 표시
- 보안상 비활성화하는 경우 많음

**nginx 옵션:**

- autoindex on: 디렉터리 목록 자동 생성
- autoindex_exact_size off: 사람이 읽기 쉬운 크기 (KB, MB)
- autoindex_localtime on: 로컬 시간으로 표시

---

### 4.4 동적 콘텐츠 리소스 매핑

**정적 콘텐츠:**

- HTML, CSS, 이미지 등
- 파일을 그대로 반환

**동적 콘텐츠:**

- PHP, Python, Ruby 등으로 생성
- 요청에 맞게 콘텐츠 실시간 생성

**nginx에서 동적 콘텐츠 처리:**

- PHP: FastCGI로 PHP-FPM에 전달
- Python: uWSGI, Gunicorn 등 사용
- Node.js: 리버스 프록시로 연결

---

### 4.5 접근 제어

**IP 기반 접근 제어:**

- 특정 IP만 허용
- 예: 관리자 페이지는 내부 네트워크만 접근

**인증 기반 접근 제어:**

- Basic 인증: 사용자명/비밀번호
- Digest 인증: 암호화된 인증
- OAuth, JWT 등: 현대적인 방법

**nginx 접근 제어:**

- allow: IP 허용
- deny: IP 거부
- auth_basic: 기본 인증
- auth_basic_user_file: 사용자 파일 위치

---

## 5. MIME 타입 결정

### 왜 중요한가?

브라우저는 Content-Type 헤더를 보고 어떻게 렌더링할지 결정합니다:

- Content-Type: text/html → HTML로 파싱
- Content-Type: image/jpeg → 이미지로 표시
- Content-Type: application/pdf → PDF 뷰어로 열기

잘못된 MIME 타입:

- HTML 파일을 text/plain으로 보내면 → 소스코드 그대로 표시
- 실행 파일을 잘못 보내면 → 보안 문제 발생

---

### MIME 타입 결정 방법 4가지

#### 방법 1: mime.types (파일 확장자 매핑)

**가장 일반적인 방법**

**동작 방식:**

- 파일 확장자를 보고 MIME 타입 결정
- .html → text/html
- .jpg → image/jpeg
- .json → application/json

**mime.types 파일 예시:**

- text/html: html, htm, shtml
- text/css: css
- image/jpeg: jpeg, jpg
- application/json: json

**nginx 사용:**

- mime.types 파일 포함
- default_type으로 기본값 설정 (보통 application/octet-stream)

**장점:**

- 빠르고 효율적
- 설정 간단

**단점:**

- 확장자 없으면 대응 불가
- 확장자 위조 가능

**2026년 현재:**

- 여전히 가장 보편적인 방식

---

#### 방법 2: 매직 타이핑 (Magic Typing)

**파일 내용 검사로 타입 결정**

**동작 방식:**

- 파일 시작 부분의 매직 넘버(바이트 패턴) 확인
- 실제 파일 타입 식별

**주요 매직 넘버:**

- JPEG: FF D8 FF
- PNG: 89 50 4E 47
- GIF: 47 49 46 38
- PDF: 25 50 44 46 (%PDF)

**Unix file 명령어:**

- file logo.png
- → PNG image data, 512 x 512, 8-bit/color RGBA

**장점:**

- 실제 파일 타입 정확히 판별
- 확장자 위조 방지

**단점:**

- 파일 읽기 오버헤드
- 성능 영향

**2026년 현재:**

- 파일 업로드 검증 시 mime.types와 병행 사용
- 보안이 중요한 곳에서 사용

---

#### 방법 3: 명시적 타이핑 (Explicit Typing)

**특정 파일/디렉터리에 MIME 타입 강제 지정**

**사용 사례:**

**1. 커스텀 확장자**

- .special 파일 → application/x-custom-type

**2. API 엔드포인트**

- /api/ 경로 → 항상 application/json

**3. 다운로드 강제**

- /downloads/ → application/octet-stream + Content-Disposition

**장점:**

- 커스텀 확장자나 특수 경우 유연 대응
- 기본값 오버라이드 가능

**단점:**

- 설정 파일 관리 필요

**2026년 현재:**

- 특수 경우나 기본값 오버라이드 시 사용

---

#### 방법 4: 유형 협상 (Type Negotiation)

**클라이언트 선호도 기반 선택**

**동작 방식:**

**클라이언트 요청:**

- GET /data HTTP/1.1
- Accept: application/json, application/xml;q=0.9, _/_;q=0.8

**해석:**

- 1순위: application/json
- 2순위: application/xml (q=0.9)
- 3순위: 기타 (_/_; q=0.8)

**서버 응답:**

- 가능하면 application/json으로 응답
- 없으면 application/xml
- 둘 다 없으면 기타

**품질 값 (q-value):**

- 0.0 ~ 1.0 범위
- 생략 시 1.0
- 선호도 표현

**장점:**

- 클라이언트 친화적
- 같은 리소스를 다양한 형식으로 제공
- REST API 표준

**단점:**

- 구현 복잡도 증가
- 캐싱 복잡해짐 (Vary 헤더 필요)

**2026년 현재:**

- REST API에서 표준으로 사용
- Content Negotiation은 HTTP의 핵심 기능

---

### MIME 타입 결정 우선순위

**실제 웹서버 처리 순서:**

**1. 명시적 타이핑**

- 설정 파일에 직접 지정된 경우

**2. 유형 협상**

- Accept 헤더가 있고 서버가 지원하는 경우

**3. 매직 타이핑**

- 보안 설정이 활성화된 경우

**4. mime.types**

- 기본 방식

**5. 기본값**

- application/octet-stream 등

---

## 6. 리다이렉션

### 리다이렉션이란?

웹서버가 클라이언트에게 "다른 곳으로 가세요"라고 알려주는 것

**응답:**

- HTTP/1.1 301 Moved Permanently
- Location: https://new-domain.com/

**브라우저 동작:**

- 자동으로 새 URL로 요청

---

### 리다이렉션 종류

#### 301 Moved Permanently (영구 이동)

**의미:**

- 리소스가 영구적으로 다른 곳으로 이동

**브라우저 동작:**

- 북마크 갱신
- 다음부터는 새 URL로 바로 접속

**검색엔진:**

- 새 URL을 인덱싱
- 오래된 URL 점수를 새 URL로 이전

**사용 사례:**

- 도메인 변경
- 사이트 구조 개편

---

#### 302 Found (임시 이동)

**의미:**

- 리소스가 임시로 다른 곳에 있음

**브라우저 동작:**

- 북마크 유지
- 다음에도 원래 URL로 접속

**검색엔진:**

- 원래 URL 유지
- 새 URL 인덱싱 안 함

**사용 사례:**

- 점검 중 임시 페이지
- A/B 테스트

---

#### 기타 리다이렉션

**303 See Other:**

- GET으로 메서드 변경
- POST 후 GET으로 리다이렉트 (PRG 패턴)

**307 Temporary Redirect:**

- 메서드 유지하는 임시 리다이렉션
- POST → POST 유지

**308 Permanent Redirect:**

- 메서드 유지하는 영구 리다이렉션
- POST → POST 유지

---

### 리다이렉션 사용 사례

#### 1. HTTP → HTTPS 강제

**왜?**

- 보안 (암호화)
- SEO (검색엔진 최적화)

**동작:**

- http://example.com → https://example.com

---

#### 2. www 정규화

**www 추가:**

- example.com → www.example.com

**www 제거:**

- www.example.com → example.com

**왜?**

- URL 일관성
- 쿠키 도메인 관리
- SEO

---

#### 3. URI 증강 (상태 정보 추가)

**동작:**

- /app → /app?sid=abc123

**목적:**

- 세션 ID를 URL에 추가
- 트랜잭션 간 상태 유지
- 쿠키 대신 URL 사용

---

#### 4. 부하 균형

**과부하 서버:**

- 요청이 너무 많음

**동작:**

- → https://backup-server.com으로 리다이렉트

**실제로는:**

- 리다이렉션보다 로드 밸런서 사용

---

#### 5. 디렉터리 슬래시 정규화

**문제:**

- /images (슬래시 없음)
- /images/ (슬래시 있음)
- 다른 URL로 인식될 수 있음

**해결:**

- /images → /images/ (301 리다이렉트)

**이유:**

- 상대 경로 문제 방지
- SEO 중복 콘텐츠 방지

---

#### 6. 모바일 분기

**User-Agent 확인:**

- mobile, android, iphone 등

**동작:**

- 모바일 → https://m.example.com
- PC → https://www.example.com

**현대적 방법:**

- 반응형 웹 디자인 (리다이렉션 불필요)

---

### 상태 코드 비교

| 코드 | 의미            | 브라우저 동작 | 검색엔진      |
| ---- | --------------- | ------------- | ------------- |
| 301  | 영구 이동       | 북마크 갱신   | 새 URL 인덱싱 |
| 302  | 임시 이동       | 북마크 유지   | 원래 URL 유지 |
| 303  | See Other       | GET으로 변경  | -             |
| 307  | 임시 리다이렉션 | 메서드 유지   | 원래 URL 유지 |
| 308  | 영구 리다이렉션 | 메서드 유지   | 새 URL 인덱싱 |

# Part 2: 프록시 (6장)

## 1. 프록시란 무엇인가

### 프록시의 정의

**프록시 = 클라이언트와 서버 사이의 중개자**

**위치:**

- 클라이언트 ←→ 프록시 ←→ 서버

**역할:**

- HTTP 메시지를 중간에서 처리
- 필터링, 수정, 로깅 등

**프록시의 이중 역할:**

- 클라이언트 입장: 웹 **서버**처럼 동작
- 서버 입장: 웹 **클라이언트**처럼 동작

---

### 프록시 vs 게이트웨이

**프록시:**

- HTTP ←→ [프록시] ←→ HTTP
- 같은 프로토콜 사용

**게이트웨이:**

- HTTP ←→ [게이트웨이] ←→ FTP/DB/기타
- 프로토콜 변환

**실제로는 구분이 모호함**

- HTTP to HTTPS 프록시는 게이트웨이?
- 용어가 혼용되는 경우 많음

---

## 2. 프록시의 종류와 용도

### 2.1 개인 프록시 vs 공용 프록시

#### 개인 프록시 (Private Proxy)

- 하나의 클라이언트 전용
- 예: 브라우저 확장 프로그램 프록시
- VPN

#### 공용 프록시 (Public Proxy)

- 여러 클라이언트 공유
- 중앙 집중식 관리
- 비용 효율적
- 회사, ISP 프록시

---

### 2.2 프록시 사용 목적

#### 1. 어린이 필터 (콘텐츠 필터링)

**동작:**

- 특정 사이트 차단
- 유해 콘텐츠 필터링

**예시:**

- adult-site.com → 403 Forbidden
- gambling.com → 차단

---

#### 2. 보안 방화벽

**동작:**

- 외부 접근 차단
- 내부 네트워크 보호

**예시:**

- 내부 IP만 허용: 192.168.1.0/24
- 외부는 모두 거부

---

#### 3. 웹 캐시

**동작:**

- 자주 요청되는 콘텐츠 저장
- 다음 요청 시 캐시에서 제공

**장점:**

- 응답 속도 향상
- 대역폭 절약
- 서버 부하 감소

**캐시 상태:**

- HIT: 캐시에서 제공
- MISS: 원 서버에서 가져옴

---

#### 4. 대리 프록시 (리버스 프록시)

**포워드 프록시 vs 리버스 프록시:**

**포워드 프록시:**

- 클라이언트 → [프록시] → 인터넷 → 여러 서버들
- 클라이언트가 프록시 설정
- 클라이언트를 대신해서 요청

**리버스 프록시:**

- 여러 클라이언트 → 인터넷 → [프록시] → 백엔드 서버
- 클라이언트는 프록시 존재 모름
- 서버를 대신해서 응답

**리버스 프록시 역할:**

- 보안 (실제 서버 숨김)
- SSL/TLS 종료 (암호화 처리)
- 로드 밸런싱
- 캐싱

---

#### 5. 콘텐츠 라우터

**동작:**

- 요청 내용에 따라 다른 백엔드로 전달

**예시:**

- 이미지 → 이미지 서버
- 동영상 → 미디어 서버
- API → API 서버
- 기타 → 웹 서버

---

#### 6. 트랜스코더

**동작:**

- 콘텐츠 형식 변환

**예시:**

- 이미지 리사이징
- 동영상 인코딩
- 압축

---

#### 7. 익명화 프록시

**동작:**

- 신원 정보 제거

**제거하는 정보:**

- User-Agent (브라우저 정보)
- Referer (이전 페이지)
- Cookie (쿠키)
- X-Forwarded-For (IP 주소)

**목적:**

- 프라이버시 보호
- 익명성 보장

---

## 3. 프록시 배치 전략

### 3.1 프록시 서버 배치 위치

**전체 흐름:**

- [클라이언트] ←→ [출구 프록시] ←→ 인터넷 ←→ [입구 프록시] ←→ [대리 프록시] ←→ [서버]

---

#### 1. 출구 프록시 (Egress Proxy)

**위치:**

- 회사 네트워크 출구

**역할:**

- 직원들이 인터넷 나가는 트래픽 제어

**기능:**

- 특정 사이트 차단
- 업무 시간 제한
- 로깅 (누가 어디 접속했는지)

**예시:**

- 업무 시간엔 YouTube 차단
- 모든 외부 접속 기록

---

#### 2. 접근(입구) 프록시 (Access/Ingress Proxy)

**위치:**

- ISP 네트워크

**역할:**

- 고객들의 요청 종합 처리

**기능:**

- 인기 콘텐츠 캐싱
- 대역폭 절약
- 다운로드 속도 향상

**예시:**

- Netflix 인기 영화 캐싱
- YouTube 자주 보는 영상 저장

---

#### 3. 대리 프록시 (Surrogate/Reverse Proxy)

**위치:**

- 웹 서버 앞단

**역할:**

- 실제 서버를 대신해서 응답

**기능:**

- 보안 (실제 서버 IP 숨김)
- SSL/TLS 처리
- 로드 밸런싱
- 캐싱
- DDoS 방어

**예시:**

- www.example.com의 실제 서버는 3개
- nginx가 앞에서 부하 분산

---

#### 4. 네트워크 교환 프록시

**위치:**

- 인터넷 피어링 지점

**역할:**

- 인터넷 혼잡 완화
- 트래픽 흐름 감시

**기능:**

- 대용량 캐시
- 트래픽 통계
- 대역폭 절약

---

### 3.2 프록시 계층 (Proxy Hierarchy)

**구조:**

- 클라이언트
  - ↓
- 자식 프록시 (엣지)
  - ↓ (캐시 미스)
- 부모 프록시 (중앙)
  - ↓ (캐시 미스)
- 원 서버

**부모-자식 관계:**

- 자식: 클라이언트와 가까운 프록시
- 부모: 원 서버와 가까운 프록시

**동작:**

1. 클라이언트 → 자식 프록시
2. 자식 캐시 확인 → HIT면 즉시 응답
3. MISS면 부모 프록시로
4. 부모 캐시 확인 → HIT면 응답
5. MISS면 원 서버로
6. 응답을 캐시에 저장하며 돌아옴

**장점:**

- 계층적 캐싱
- 부하 분산
- 지역별 최적화

---

### 3.3 동적 부모 선택

프록시가 여러 부모 중 하나를 선택하는 방법

#### 1. 부하 균형 (Load Balancing)

**알고리즘:**

- 라운드 로빈: 순서대로
- 최소 연결: 연결 수 가장 적은 곳
- 응답 시간: 가장 빠른 곳

---

#### 2. 지리적 라우팅

**동작:**

- 클라이언트 위치 확인
- 가장 가까운 서버로

**예시:**

- 한국 사용자 → kr-backend
- 미국 사용자 → us-backend
- 일본 사용자 → jp-backend

---

#### 3. 프로토콜/타입 라우팅

**동작:**

- 콘텐츠 타입에 따라 다른 서버

**예시:**

- 이미지 → image-server
- 동영상 → video-server
- API → api-server

---

#### 4. 유료 서비스 라우팅

**동작:**

- 구독자 여부 확인
- VIP는 고성능 서버로

**예시:**

- 무료 사용자 → 일반 서버
- 프리미엄 사용자 → 고성능 서버

---

## 4. 프록시 요청의 특징

### 4.1 프록시 URI vs 서버 URI

#### 서버 직접 요청 (부분 URI):

**요청:**

- GET /index.html HTTP/1.1
- Host: www.example.com

**특징:**

- URI에 호스트 정보 없음
- Host 헤더로 서버 식별

---

#### 프록시 통한 요청 (완전 URI):

**요청:**

- GET http://www.example.com/index.html HTTP/1.1
- Host: www.example.com

**특징:**

- URI에 호스트 정보 포함
- 스킴, 호스트, 포트 모두 명시

**왜 완전 URI가 필요한가?**

- 프록시는 어느 서버로 연결할지 알아야 함
- URI만 보고 목적지 파악

---

### 4.2 가상 호스팅 문제

**문제:**

- 여러 사이트가 같은 IP 공유
- IP만으로는 어느 사이트인지 구분 불가

**해결: Host 헤더**

- GET /index.html HTTP/1.1
- Host: www.example.com ← 이걸로 구분

**왜 필요한가?**

- 하나의 서버에 여러 도메인
- 가상 호스팅 구현

---

### 4.3 인터셉트 프록시 (투명 프록시)

**특징:**

- 클라이언트는 프록시 존재를 모름
- 부분 URI 전송
- 네트워크 레벨에서 트래픽 가로채기

**동작:**

- 라우터/스위치에서 HTTP 트래픽 가로채기
- 프록시로 리다이렉트
- 프록시가 처리 후 원 서버로

**장점:**

- 클라이언트 설정 불필요
- 투명하게 동작

**단점:**

- Host 헤더로 목적지 파악 필요
- 설정 복잡

---

### 4.4 URI 자동확장의 차이

#### 프록시 없을 때:

- 사용자 입력: "yahoo"
- 브라우저: "www.yahoo.com"으로 자동 확장
- 정상 동작

---

#### 명시적 프록시 사용 시:

- 사용자 입력: "yahoo"
- 브라우저: 자동 확장 안 함 (프록시가 알아서 하겠지)
- 프록시: "yahoo" 서버 찾으려 시도
- 결과: 실패 가능

**이유:**

- 프록시가 자체 DNS를 가질 수 있음
- 사용자 의도와 다른 사이트로 갈 수 있음

---

#### 인터셉트 프록시 사용 시:

- 사용자 입력: "yahoo"
- 브라우저: "www.yahoo.com"으로 자동 확장 (프록시 모름)
- 프록시: 투명하게 중계
- 정상 동작

---

## 5. Via 헤더와 메시지 추적

### 5.1 Via 헤더

**목적:**

- 메시지가 거쳐간 프록시 기록
- 라우팅 루프 방지
- 프로토콜 능력 파악

**문법:**

- Via: 프로토콜버전 노드이름 (코멘트)

---

**예시:**

**클라이언트 → 프록시1:**

- GET / HTTP/1.1
- Host: www.example.com

**프록시1 → 프록시2:**

- GET / HTTP/1.1
- Host: www.example.com
- Via: 1.1 proxy1.company.com

**프록시2 → 원서버:**

- GET / HTTP/1.1
- Host: www.example.com
- Via: 1.1 proxy1.company.com, 1.1 proxy2.company.com

**응답도 마찬가지로 Via 헤더 추가**

---

### 5.2 Via 헤더와 보안/프라이버시

**문제:**

- Via: 1.1 internal-proxy.company.local
- 내부 네트워크 구조 노출
- 보안 위험

**해결: 익명화**

- Via: 1.1 proxy (Company Gateway)
- 구체적인 정보 제거

**또는 완전 제거:**

- Via 헤더 자체를 제거 (비표준)

---

### 5.3 TRACE 메서드

**목적:**

- 요청이 프록시 체인을 거치며 어떻게 변경되는지 추적

**동작:**

1. 클라이언트 → TRACE / → 프록시1 → 프록시2 → 서버
2. 서버가 받은 요청을 그대로 응답으로 반환
3. 응답이 프록시를 거쳐 클라이언트로

**응답 예시:**

- HTTP/1.1 200 OK
- Content-Type: message/http
- 
- TRACE / HTTP/1.1
- Host: example.com
- Via: 1.1 proxy1, 1.1 proxy2
- X-Forwarded-For: 203.0.113.1, 198.51.100.1

**용도:**

- 디버깅
- 프록시 동작 확인
- 헤더 변경 추적

---

**보안 이슈:**

- XST (Cross-Site Tracing) 공격 가능
- 쿠키 등 민감 정보 노출 위험
- 대부분 프로덕션 환경에서 비활성화

---

### 5.4 Max-Forwards 헤더

**목적:**

- 무한 루프 방지
- 특정 프록시까지만 요청 전달

**동작:**

**클라이언트:**

- TRACE / HTTP/1.1
- Max-Forwards: 2

**프록시1:**

- Max-Forwards: 2 → 1로 감소
- 다음 홉으로 전달

**프록시2:**

- Max-Forwards: 1 → 0으로 감소
- 더 이상 전달하지 않고 응답

**용도:**

- 프록시 체인의 특정 지점 테스트
- 무한 루프 방지
- 디버깅

## Q&A

질문 있으신가요?

**예상 질문:**

**Q: Apache와 nginx 중 어떤 걸 써야 하나요?**
A: 용도에 따라 다릅니다. 대용량 트래픽과 정적 파일이 많으면 nginx, 다양한 모듈과 .htaccess가 필요하면 Apache를 추천합니다.

**Q: webserv 과제에 어떻게 활용하나요?**
A: nginx의 구조(이벤트 기반, 설정 파일 파싱 등)를 참고하되, 과제 요구사항에 맞게 단순화해서 구현하면 됩니다.

**Q: 실무에서 프록시를 꼭 써야 하나요?**
A: 대부분의 프로덕션 환경에서 리버스 프록시는 필수입니다. 보안, 성능, 유연성 면에서 큰 이점이 있습니다.
